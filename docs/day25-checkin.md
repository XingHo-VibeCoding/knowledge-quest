## 四、五轮运行记录（含两次「找误报和漏报」）

| 轮次 | 场景 | 结果 | 说明 |
|---|---|---|---|
| 1 | 首次全量实跑 | `PASS 11 · FAIL 2 · SKIP 1` | A6 真遗留 + **C1 误报** |
| 2 | 修正 C1 判据后复跑 | `PASS 12 · FAIL 1 · SKIP 1` | C1 转 PASS，仅剩 A6 |
| 3 | 更新 BUILD 到 `d25-2026-10-11` | `PASS 13 · FAIL 0 · SKIP 1` | 全绿基准 |
| 4 | **故意注入假密钥** | `PASS 12 · FAIL 1 · SKIP 1` | **A1 抓到，EXIT=1** |
| 5 | 移除探针后复跑 | `PASS 13 · FAIL 0 · SKIP 1` | 恢复确认 |

### 误报是怎么找出来并修掉的（运行 1 → 2）

**症状**：C1 报 `[FAIL] 数据库查询失败或核心表缺失`，但手动敲同样的 SQL **能查出 `cards=26 / quiz_records=6`**。

**根因**：判据有病，不是数据库有病。`tcb db execute` **不带 `--json` 时只打印给人看的表格**：

```
┌───────┬──────┐
│ cards │ quiz │
├───────┼──────┤
│  26   │  6   │
└───────┴──────┘
```

脚本却在 grep 结构化字段 `"Rows"` → 永远命中不了 → 恒定误报。

**修法**：加 `--json`，并把 `Rows` 的解析（每行是一个 JSON 字符串 `"[\"26\",\"6\"]"`）写成容错版。

> 这条正好印证 AGENTS 第 23 条：**报 FAIL 不一定是代码有病，也可能是判据有病**。

**探针本身没进仓库**：注入 → 验证 → 立即还原，`git status` 确认 `README.md` 无改动，特征词复查 0 命中。

## 六、输出格式与失败规则

**三态，不许模糊**：

```
  [PASS] A5 .env 已被忽略（.gitignore:2:.env	.env）
  [FAIL] A1 工作区命中 1 行
         ↳ bash tools/security-check.sh --offline 查看明细
  [SKIP] D1 剩余额度与到期时间 —— 控制台看，脚本拿不到
```

- 每项 `[FAIL]` 必带一行 `↳` 说明「怎么复核」。
- 末尾固定：`结果：PASS n · FAIL n · SKIP n` + 结论。
- **禁止**「看起来正常」「基本没问题」——判据必须写成"怎么算通过"。
- 有 FAIL 时退出码 = `1`；命令不存在 / 请求失败 / 证据缺失 → 一律 FAIL（或明示 SKIP 并写原因），不许默认通过。

## 九、每日一问

> **你故意弄坏哪一项来验证 Skill 不会虚报通过？**

**弄坏「硬编码密钥」这一项（A1）。** 做法是往已跟踪的 `README.md` 里追加一行含 `ghp_` + 24 位随机串的假密钥 —— 模拟真实世界里最常见的事故：「调试时临时贴了个 key，忘了删就提交了」。

选它有三个理由：

1. **它是红线项**。密钥泄露没有"影响不大"的说法，判据最不该被放宽 —— 一个只会打印 PASS 的假 Skill，在这里必然露馅。
2. **它的判据是"0 命中"这种硬数字**，没有"看起来没问题"的解释空间。
3. **它可恢复、且不动线上**。注入 → 跑 → 移除，全程只碰工作区里的一个文档文件。

**实测结果：A1 立刻报 FAIL、退出码 1，并且给出了复核命令**；移除探针后复跑回全绿。这证明 Skill 既**不会漏报**（真有问题时报了 FAIL），也**不会虚报**（问题消失后确实回到 PASS，而不是赖在 FAIL 上）。

顺带还证明了第二件事：这次实跑**新查出一个真实遗留**（A6 BUILD 过期），说明它是真的在查，不是在走过场。
