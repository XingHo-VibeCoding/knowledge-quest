**发布方式的关键认知**：这台平台**没有版本层**。`tcb hosting deploy` 的帮助原文是
*"file upload only, no version management"* —— 所以"发布 v1.0"这件事在本项目里 =
**git 打 tag（定义版本）+ 上传产物（让线上变成这一版）+ 页面上的 `BUILD` 标记（自证是哪一版）**，
三者缺一不可。这也直接决定了"回滚"只能靠 **git 历史**，不能靠平台。

## 三、回滚演练（板块 ③④）

### 3.1 三个硬数据（教材要求，没有数字 = 只写了方法没真做）

| # | 数据 | 第一轮（计时用） | 复测轮（补图用） |
|---|---|---|---|
| ① | **回滚前时间** | `2026-10-11 11:44:46` | `2026-10-11 16:26:35` |
| ② | **恢复公网可用时间** | `2026-10-11 11:45:38` | `2026-10-11 16:29:48` |
| ③ | **回退阶段总耗时** | **51 秒** | **112 秒**（上传占 98 秒） |
| ↳ | 分解 | 导出 22s + 上传 13s + 验证 14s | 导出 ~37s + 上传 98s + 验证 14s |

### 3.2 这是本项目"回滚"的真实实现（不是概念）

```
① 确认退到哪一版      git log / git tag -l        → 目标 d7b4224（Day 25 版，BUILD=d25-2026-10-11）
② 导出那一版的产物    git archive d7b4224 | tar -x -C .rollback-tmp     （123 个文件）
③ 重新上传            tcb hosting deploy .rollback-tmp / -e <envId>     （Successfully uploaded 123 file(s)）
④ 判生效（不看时间戳） 页面 js/config.js 的 BUILD 变成 d25-2026-10-11   ← 真的退回去了
⑤ 恢复                bash cloudbase/deploy.sh <envId>                  ← 回到 v1.0-2026-10-11
```

**为什么不用平台回滚**：平台上根本没有"版本"这个概念（见第二节）。所以真正的回退能力，
**完全建立在 git 有完整历史 + 有 tag 这件事上**——这也是"敢不敢用"的第一个前提。

### 3.3 耗时方差：两次差 2 倍多，这是重要结论

同一台机器、同一批 123 个文件、同一条 `hosting deploy` 命令：

| 轮次 | 上传耗时 |
|---|---|
| 第一轮 | **13 秒** |
| 复测轮 | **98 秒** |

所以回滚手册里**不能**写"回滚约 1 分钟"，只能写"**实测 13 秒 ~ 98 秒，取决于网络**，
真正耗时的是'搞清楚退到哪一版'和'确认真的退了'"。

## 五、演练中抓到的四个真实问题（这一节比"顺利跑完"有价值）

### 坑 1（Day 23 遗留，本日已根因修复）：`tcb fn deploy --path /api` 让整次部署中止

函数重发时带 `--path /api`，而 `/api` 路由在 Day 15 已建好 → CLI 在 `[CreateCloudBaseGWAPI]`
报 `Path '/api' is used` 并**中止整次部署**（exit 3）。中止点在"配置已更新、代码未上传"之间：
`tcb fn detail` 的时间戳会变（骗过肉眼），**代码却是旧的** → 线上长期是"新配置 + 旧代码"。
最好的探针是 `--metadata-file`：**CLI 只在部署走完时写它，文件不生成 = 没部署成功**。
（另：`--runtime` 只在首次部署生效，重发传它无用。）

### 坑 2（本日新增，撞了两次）：`rm -rf` 被环境的批量删除保护拦下

见 `docs/day26-drill-log.md` 第 4.1 节。**第一次**撞上后我只加了错误提示；
**第二次**（补图轮）又撞上，才明白"先删干净再重建"这条路本身不该走 ——
改为 **staging + `mv`**：构建到 `.cloudbase-dist.stage`（二十来个文件），
把旧构建目录 `mv` 进 `.cloudbase-trash/`（**mv 不是删除，不触发保护**），最后改名。

### 坑 3（本日新增）：我自己的演练脚本在撒谎

```bash
bash cloudbase/deploy.sh "$ENV" >> "$LOG" 2>&1
say "[$(ts)] deploy.sh 返回码 $?"      # ❌ $(ts) 先执行，$? 读到的是 ts 的返回码（恒为 0）
```

结果日志写着"返回码 0"，线上其实还是旧版。**"容忍失败/假报成功"这件事，
我在 Day 24 刚批评过部署脚本，转头自己的演练脚本就犯了。** 已修：先存 `$?` 再用；
并且**恢复失败就不出第三张图**（宁缺勿假）。

### 坑 4（本日新增）：CloudBase 测试域名的护栏页 + 空白图

新建浏览器 profile 首次访问 `*.tcloudbaseapp.com`，腾讯云会先塞一页
「页面访问提示 / **确定访问**」→ 脚本读到 `BUILD=null`，PrintWindow 拍到一张
**144 KB 的"风险提醒"假图**。已修两处：读取脚本**自动点掉护栏**（实测 `GUARD=clicked:确定访问`）；
`kq26_shot.py` 加**字节数自检**（< 300 KB 判"疑似空白图"并告警）——
这次的假图就是被它拦下来的。**教训：截图工具也得有判据，否则空白图会被当成证据交上去。**

### 由坑 3 顺带暴露的检查盲区（已登记，非今日修复）

`verify-project` 的 B 组查的是 **GitHub Pages** 那个域名，而演练回滚/恢复的是
**CloudBase 托管域名**。所以"前端没上传成功"这件事，**`verify-project` 是查不出来的**
（它跑不出问题，但线上确实还是旧版）。本次是靠 `deploy.sh` 第 5 步新增的
**③ 前端生效自证**（托管域名上的 `BUILD` 必须等于本地）才抓住的。
→ 待办：把 CloudBase 域名那一路也纳入 `verify-project` 的 B 组。

## 九、每日一问

**问：回滚演练花了多久？真出事你敢不敢用这套流程？**

**答**：
- **多久**：回退阶段 **51 秒**（第一轮：导出 22s + 上传 13s + 验证 14s）；
  复测轮同样流程 **112 秒**（上传变成 98s）。**差值本身就是结论——耗时随网络浮动 2 倍以上，
  能承诺的只有"几分钟内"，不是"51 秒"。**
- **敢不敢用**：**敢**，但有三个前提，缺一个就会手忙脚乱：
  1. **git 里有完整历史和 tag** —— 平台没有版本层，回退能力 100% 建在 git 上；
  2. **知道用 `BUILD` 标记判断"现在是哪一版"** —— 不看时间戳、不靠猜；
  3. **接受"回滚只治代码"** —— 数据误删只能靠发布前导出的备份重新导入。
- **不敢用的部分（诚实说）**：「数据恢复」这一环**今天没实操**（教材明确列为今日不做），
  所以它是全套流程里**唯一没被验证过的一环**。已登记，Day 27 做资源检查与备份演练时补上。
- **今天最大的收获不是"跑通了"，而是"跑挂了两次"**：一次被环境的批量删除保护拦住、
  一次被自己的假返回码骗过。**没演练过的回滚等于没有回滚——第一次撞上叫运气，第二次撞上才叫修复。**
