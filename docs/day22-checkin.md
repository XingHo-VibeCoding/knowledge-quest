## 四、防呆矩阵（「改错 / 删错」逐条实测）

> 教材要求：「操作不存在的 id 返回明确错误，不是崩溃」「删一个不存在的数据还报成功 = 防呆缺失」。

| 操作 | 输入 | HTTP | 错误码 / 返回文案 |
|---|---|---|---|
| PATCH | `id=99999`（不存在） | **404** | `CARD_NOT_FOUND`：卡片不存在，没有可改的记录（id=99999） |
| PATCH | `id=abc` / `id=0` | **400** | `BAD_ID`：id 必须是正整数 |
| PATCH | 空请求体 `{}` | **400** | `EMPTY_PATCH`：没有要修改的内容（把可改字段列清楚）——**不静默成功** |
| PATCH | 夹带 `id` / `source` | **400** | `IMMUTABLE_FIELD`：字段「id（数据库主键）」「来源（服务端记账字段）」不能修改——**不静默忽略** |
| PATCH | 夹带不认识的字段 | **400** | `UNKNOWN_FIELD` |
| PATCH | 题面 201 字 / 难度 9 | **400** | `VALIDATION_ERROR`：与 `POST` 同一套校验口径与文案 |
| PATCH | 改题面撞上同科目已有卡 | **409** | `DUPLICATE_CARD`：唯一性口径与 `POST` 完全一致 |
| PATCH | 题面填成原值（等于没变） | **200** | **不被自己的旧值判成重复**（这条最容易写错） |
| DELETE | `id=99999`（不存在） | **404** | `CARD_NOT_FOUND`：没有可删的记录——**绝不返回 200 假成功** |
| DELETE | 内置卡 `source=mock` | **403** | `NOT_DELETABLE`：只有 `source=user` 的卡可删（内置卡删掉要重灌种子数据） |
| DELETE | `id=abc` | **400** | `BAD_ID` |
| DELETE | 同一 id 删第二次 | **404** | `CARD_NOT_FOUND` |

**无一条返回 5xx**（没有 500 裸报错），**无一条「假成功」**。

### 4.1 删除的三层护栏（各管一段，缺一不可）

| 层 | 位置 | 拦什么 | 为什么放这一层 |
|---|---|---|---|
| ① 只读卡保护 | 服务端 `cardsService.remove()` | `source !== 'user'` → 403 | 放在**最里面**：绕过前端直接调接口也拦得住 |
| ② 存在性校验 | 服务端 `cardsService.remove()` | 查不到 → 404 | 删不存在的 id 报「成功」是最典型的防呆缺失 |
| ③ 二次确认 | 前端 `tools/checkup.html` | 第一次点击只上膛，第二次才发请求 | 不可逆操作的**最后一道人肉闸门**，放在最外面是为了「手滑也删不掉」 |

## 九、每日一问

> **删除为什么比新增更容易出事？你在哪加了确认？**

**因为新增是「加」，删除是「减」，而人类对「减」的容错是零。** 具体说有三层不对称：

1. **可逆性不对称**：新增错了最坏是库里多一行垃圾，再删掉就行；删除错了**数据就没了**，没有「撤销」这个动作。所以我今天给删除单独设了「不可逆操作」的待遇。
2. **影响面不对称**：新增只影响自己那一行；删除会牵动别处——`quiz_records.card_ids` 是弱关联（历史战绩里可能记着这张卡的 id）。这也是 Day 16 当初**故意不建外键**的原因：删卡不该把历史成绩一起带走。
3. **失败信号不对称**：新增失败很容易发现（页面上没出现新卡）；删除失败**长得很像成功**——如果接口对不存在的 id 也回 `200 {"ok":true}`，页面照样显示「已删除」，用户以为删了、库里其实什么都没有。所以我把「删不存在的 id 必须 404」当成硬指标来测（第四节第 9 条）。

**确认加在三处，从外到内：**
- **最外（人）**：检查台上删除按钮要**点两次**——第一下只把按钮改写成「确认删除 id=N？」，第二下才真的发请求；
- **中间（业务）**：`remove()` 先查这张卡在不在，不在就 **404**，绝不给「假成功」；
- **最里（数据）**：`source !== 'user'` 的内置卡一律 **403**——哪怕有人绕过页面直接调接口，种子数据也删不掉。

一句话：**新增可以「宽进」，删除必须「严出」。** 我今天写代码的时间，估计有三成花在了「怎么让删不掉、改不坏」上。
