## 四、⚠️ 体检发现：静态托管站泄露了整个项目（今日最高优先级问题）

### 4.1 怎么发现的

体检托管站文件清单时，`tcb hosting list` 报 **122 个文件**，而本地构建产物只有 **20 个**。
多出来的都是什么？拉全清单后看到了不该在站点上的名字：

```
AGENTS.md  PRD.md  README.md  TECH_DESIGN.md  DESIGN_RULES.md  research.md  api-contract.md
cloudbaserc.json
cloudbase/deploy.sh
cloudbase/functions/api/{index,server}.js  ...（云函数全部源码，12 个）
db/schema.sql  db/seed.sql  db/verify.sql
docs/... （75 个，含各天打卡文档、可用性测试记录、截图）
tools/{security-check,backup-data,verify-project,clean-trash}.sh
```

### 4.2 定性：真的能在公网下载吗（不看清单，看响应）

不看"清单里有"，而是**逐个 curl**，因为判据必须是"公网真的拿得到"：

| 路径 | HTTP | 结论 |
|---|---|---|
| `/AGENTS.md` | **200** | 内部协作规则，公网可读 |
| `/TECH_DESIGN.md` | **200** | 架构文档（45 KB）公网可读 |
| `/api-contract.md` | **200** | 接口契约公网可读 |
| `/cloudbase/deploy.sh` | **200** | **实测返回脚本正文**（第一行是 `#!/usr/bin/env bash`） |
| `/cloudbase/functions/api/server.js` | **200** | 云函数源码公网可读 |
| `/db/schema.sql` | **200** | 数据库结构公网可读 |
| `/docs/day15-checkin.md` | **200** | 打卡文档公网可读 |
| `/tools/security-check.sh` | **200** | 内部审计脚本（含扫描特征词）公网可读 |
| `/.env` | 404 | ✅ 凭据本体没被传上去 |
| `/backups/*.json` | 404 | ✅ 数据备份没被传上去 |

**结论：泄露是真的，但凭据没有被波及**（`.env` 与 `backups/` 都不在站上）。
这就是要立刻处理的理由 —— 拖下去只是扩大暴露面。

### 4.3 根因（不是"手滑"，是流程缺陷）

时间戳把过程说得很清楚：这些文件的 `lastModified` 都是 **2026-10-11 16:26:48~49**，
而 `index.html` 是 **16:29:03**。16:26 正是 Day 26 回滚演练的执行窗口。

**根因链**：

1. Day 26 回滚手册写的是 `git archive <目标commit> | tar -x -C "$ROLLBACK_TMP"`
   —— `git archive` 从**仓库根**导出，拿到的是**整个仓库快照**，不是"前端产物"。
2. 接着 `tcb hosting deploy "$ROLLBACK_TMP" /` 把这个快照目录整个传到了站点根 `/`。
3. 而 `tcb hosting deploy` 是 **只覆盖、不删除**的（CLI 原话："file upload only, no version management"）
   —— 于是这 102 个文件**永久留在公网**，之后每次正常部署 `deploy.sh` 都不会碰它们。
4. 叠加一个更早的疏漏：`deploy.sh` 的构建白名单写的是 `cp -r ... "$PROJ/tools"`，
   把 `tools/` 整个目录（含 4 个 `.sh`）也发上了站点。

**三个缺陷叠在一起，才出现"源码在官网上躺了一整天没人发现"。**

### 4.4 修复（三层，缺一层都不算修好）

| 层 | 动作 | 文件 |
|---|---|---|
| ① 止损 | 清掉站上 102 个不该公开的文件（docs/ cloudbase/ db/ backups/ 根目录文档 / `tools/*.sh`） | 一次性执行，由 ② 自动化 |
| ② 不再犯 | `deploy.sh` 构建改**真白名单**（`index.html` + `css/ js/ data/` + **只发 `tools/*.html`**）；并在每次上传前**自动清掉站上已知的残留目录/文件**（先用 `hosting list --json` 取现状，干净时不产生任何删除调用） | `cloudbase/deploy.sh` |
| ③ 能发现 | 新增**第 5 步 ④「站点白名单自证」**：站上文件集合必须 ⊆ 白名单正则，否则部署判定失败、退出码非 0；同时给回滚手册换成 `git worktree` + 跑**同一个** `deploy.sh`（回退与发布共用一条构建路径，就不再有两套白名单） | `cloudbase/deploy.sh`、`docs/day26-rollback-manual.md` |

白名单正则（唯一真源，脚本与检查共用同一表达式）：

```
^(index\.html|css/|js/|data/|tools/[^/]+\.html$|__auth/|cloud-admin/)
```

> `__auth/` 与 `cloud-admin/` 是 CloudBase 平台自己生成的文件（环境创建当天就有），必须保留。

### 4.5 复验（修完必须回头看公网，不看日志）

`bash cloudbase/deploy.sh <envId>` → **EXIT=0**，第 5 步四项自证全过：

```
  [health]     OK   后端活着
  [新版行为]   OK   5xx 走统一出口（INTERNAL_ERROR + traceId）
  [前端生效]   OK   托管域名上的 BUILD = 本地（v1.0-2026-10-11）
  [站点白名单] OK   站上只有白名单内容（共 20 个文件）
```

公网侧逐个复验（这才是判据）：

| 检查 | 结果 |
|---|---|
| 17 个"不该公开"的路径（AGENTS.md / deploy.sh / server.js / schema.sql / docs/* / tools/*.sh …） | **全部 404** |
| 8 个"应该能访问"的路径（`/` `/index.html` `/css/style.css` `/js/config.js` `/js/main.js` `/data/quest-cards.json` `/tools/api-live.html` `/tools/checkup.html`） | **全部 200** |
| 站上文件数 | **122 → 20** |
| 站点体积 | **27.74 MB → 约 0.4 MB** |
| 发布前检查 | `PASS 14 · FAIL 0 · SKIP 1`（新增的 **B7 站点白名单** 首次即为 PASS） |

## 六、如果明天环境没了，用这份备份 + 仓库代码，多久能恢复？

**答：分两种情况 ——**

**情况 A：环境还在，只是数据被误删/写坏**（最常见）
用 `backups/*.json` 重新导入两张表。**约 5 分钟**：
建表 + 灌种子有现成脚本（`db/schema.sql`、`db/seed.sql`），导入是两条 SQL，没有需要等的外部流程。
> 注意：这一步是**唯一没有实操演练过**的环节（Day 26 明确列为「今日不做」）。
> 所以这个"5 分钟"是**估算**，不是实测 —— 如实标注。Day 28 前若有机会补一次导入演练，这个数字才算落地。

**情况 B：整个环境到期被回收**（第七节的场景）
需要重建环境 + 重新部署，**约 20–30 分钟**，其中**人工步骤占大头**：

| 步骤 | 有据可查的耗时 |
|---|---|
| 在控制台新建环境（体验版） | 人工操作，**未计时**（Day 16 建环境时没有记录） |
| 跑 `db/schema.sql` 建表 | 秒级 |
| 跑 `db/seed.sql` 灌种子 + 导入 `backups/` 两张表 | 秒级 |
| `bash cloudbase/deploy.sh <envId>`（构建 + 上传 + 四项自证） | **约 53 秒**（Day 26 发布 v1.0 实测） |
| 重新绑定路由 `/api` + 改 `js/config.js` 里的域名 + 重新部署 | 约 2 分钟 |
| 云函数首次部署 | 未单独计时 |

**所以诚实的答案是：数据这一半是分钟级（秒级 SQL），整个环境的重建是"半小时级"，
不确定性全在控制台那一步人工操作上。** 这也反过来印证了第一节那句：
**当下的主要风险不是额度，是"只有一份环境"**。若这个作品要用下去，值得考虑到期前把环境续上。
