## 三、主任务｜Bug #1：⑤ 面板的「防呆检测」静默失败

### 3.1 现象 / 复现步骤 / 报错原文 / 已尝试动作

- **现象**：点「拿不存在的 id 试一次（99999）」之后，徽章停在「⏳ 防呆检测中」，结果框还是「尚未测试」，**永远不给结论**。
- **复现步骤**：打开 `tools/checkup.html` → 滚到第 ⑤ 面板 → 点「拿不存在的 id 试一次（99999）」→ 观察徽章与结果框（连做 3 次）。
- **报错原文**（用调试器 `Debugger.setPauseOnExceptions('all')` 抓下来的真实异常）：
  ```
  ReferenceError: r1 is not defined
      at tools/checkup.html:713:55
  （reason: promiseRejection）
  ```
- **已尝试动作**：刷新页面重试 3 次 → 每次现象一致；用调试器断在异常处 → 定位到 713 行。

### 3.2 原因排序与逐个排除

| 排序 | 猜测的原因 | 验证方法 | 结论 |
|---|---|---|---|
| ① | promise 链里引用了作用域外的变量 | 调试器暂停在异常点看行号 | **命中** —— 异常就抛在 713 行，`r1` 是第一个回调的形参 |
| ② | `apiFetch` 返回的结构不对，`res.status` 取不到 | 看 `__KQ_EVIDENCE().lastMissing` | 排除 —— 两个 404 的完整响应体都在，说明结构正常 |
| ③ | `missLine()` 内部抛错 | 看异常类型 | 排除 —— 抛的是 `ReferenceError`（变量查找失败），不是函数内部错误 |
| ④ | 网络 / CORS 问题让请求挂住 | 看「请求去向」面板 | 排除 —— PATCH 404、DELETE 404 都回来了，网络层没问题 |

**排除的逻辑主线**：`lastMissing` 里两个响应体都齐 → 说明**请求链路是通的**；异常类型是 `ReferenceError` 而不是网络错 → 问题一定在**收到响应之后的代码**里；异常行号落在第二个 `.then` 的回调内 → 那就是 `r1` 在那儿不可见。

### 3.3 根本原因

```js
return apiFetch('PATCH', '/cards/' + MISS, {...})
  .then(function (r1) {          // r1 只活在这个回调的形参作用域里
    out.PATCH = { status: r1.status, body: r1.body };
    return apiFetch('DELETE', '/cards/' + MISS);
  })
  .then(function (r2) {
    ...
    $('editJson').textContent = missLine('PATCH', r1) + '\n' + missLine('DELETE', r2);
    //                                    ^^^ 这里根本看不到 r1 → ReferenceError
  });
```

而挂载点是 `tryMissing().catch(function () {})` —— **一个空的 catch 把这个异常吃掉了**，所以控制台里连红字都没有。
两个 404 明明都收到了、数据也记进 `state.lastMissing` 了，页面却停在「检测中」：**最坏的失败形态是静默失败**。

> 这个 Bug 是 **Day 22 的提交 `0b6ad01` 引入的**（`git log -S "missLine('PATCH', r1)"` 可查），从那天起一直在。Day 22 的防呆验收走的是「curl 直打接口」，所以接口层是真的过了；**页面按钮这条路径当天没跑到，失败又被空 catch 吞了**，于是漏了一整天。

### 3.4 修复

```js
var firstRes = null;                       // ← 把第一个响应提到函数作用域
return apiFetch('PATCH', ...)
  .then(function (r1) { firstRes = r1; ... })
  .then(function (r2) { ... missLine('PATCH', firstRes) ... });
```

挂载点也不再空吞：

```js
$('btnTryMissing').addEventListener('click', function () {
  tryMissing().catch(function (e) {
    badge($('editBadge'), 'bad', '❌ 检测中断');
    msg($('editMsg'), 'bad', '防呆检测没能跑完：' + ((e && e.message) || e) + '（原因已打到控制台，可复制给开发者）');
    console.error('[KQ][checkup] tryMissing 中断：', e);
  });
});
```

**边界**：只改了这一个挂载点。同页还有 10 处同类空 catch，登记为待办（见第九节），今天不扩大改动范围。

### 3.5 验证

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 连续 3 次，页面给出结论 | **0/3**（3 次都静默失败） | **3/3** |
| 抛出的异常 | `ReferenceError: r1 is not defined` ×3 | **0 次** |
| 徽章 | ⏳ 防呆检测中 | ✅ 防呆通过 · 两条都 404 |
| 结果框 | 尚未测试 | 两条 404 的中文说明（`CARD_NOT_FOUND`） |

证据图：`docs/screenshots/kq_day24_f12_before.png`（F12 报错现场）、`kq_day24_f12_after.png`（修复后在线上站点的正常运行）。

## 四、余力加练｜Bug #2：② 面板的读取语义全错

**现象**：库里 26 行，页面写「库内总行数 **5 行**」；表格自称「最新 5 行」，实际列的是 **id 1~5（最旧的 5 张）**；写完一条新卡，点「重新读取」**看不到它** —— 而写入成功的提示明说「点『重新读取』就能在列表里看到它」。

**根因**（两处叠加，都不是「代码写错了」而是「语义理解错了」）：

1. 后端列表固定 `order: 'id.asc'`（`cardsRepository.js`），前端却用 `?limit=5` 直接把这 5 条当「最新 5 行」→ 拿到的是**最旧**的 5 条。新写入的行 id 更大，永远进不了这 5 条。
2. 接口的 `count` 按契约是**本页条数**（`api-contract.md` 第 63 行写着「本页条数，方便前端核对」），页面却把它当「库内总行数」——所以库里 26 行、页面显示 5 行。

**修复**：一次读满上限（`limit=200`）→ 自己按 id 倒序取最新 5 条展示；行数用**实际读到的条数**；「库内最新一条」也在**全部读到的行**里取 `created_at` 最大值。顺带把标签文案改准，不再自称「count 字段」。

**验证**：启动基线由「5 行」变为 **26 行**；写完立刻回读 → 总数 27、新行出现在表格里。

> 这里有个自我提醒：**这不是「代码写错了」，是我当初把契约读成了自己想要的意思**。`count` 的定义就在契约第 63 行，写得很清楚。

## 五、意外收获｜Day 23 的云函数部署实际没生效

排查 Bug #4/#5 时发现：并发双删返回的 500 里，错误码是 **`DB_ERROR`**、且**不带追踪号** —— 而 Day 23 我已经把 5xx 统一成 `INTERNAL_ERROR` + 必带 `traceId`，提交 `f045381` 也确认改到了（`git show f045381:...cardsService.js` 第 197 行就是 `INTERNAL_ERROR`）。

**取到的证据**：

| 探测 | 结果 | 说明 |
|---|---|---|
| `GET /api/cards/<超大数字>` ×15 | 15/15 都是 `500 INTERNAL_ERROR` + traceId | 入口层的 Day 23 改动**在线上** |
| 并发双删 ×5 | 4/5 返回 `500 DB_ERROR`（无 traceId） | service 层的 Day 23 改动**不在线上** |
| 重新部署后并发双删 ×6 | 5/6 返回 `500 INTERNAL_ERROR` **+ traceId** | 修复确认 |

**结论**：Day 23 那次 `FORCE_FN=1 bash cloudbase/deploy.sh` 虽然返回了 `rc=3`、`tcb fn detail` 的 Modification time 也变了，但**代码实际没有更新上去**（线上是「新入口层 + 旧业务层」的混合状态）。今天重新部署后，5xx 才真正走统一出口。

**这条教训比 Bug 本身值钱**：

- `tcb fn deploy` 返回 rc=3 时，**不能用 `fn detail` 的 Modification time 当作「已生效」的证据**；
- 判断部署是否生效，只能打一个**只在新版才成立的行为**（今天用的就是「并发路径的错误码 + 有没有 traceId」）；
- Day 23 我只验了一条路径（`GET` 的超大 id），恰好那条路径走的是新入口层，于是给出了「已上线」的结论 —— **验收抽样没覆盖到的分支，等于没验**。

> 工具链风险另记一笔：`tcb fn detail` 会把函数环境变量里的 API Key **明文**打印出来（这是 Day 23「审计脚本泄露密钥」同类问题的第二次）。本次输出未写入任何文件/文档/截图；`AGENTS.md` 第 20 条已补上「这条命令必须管道脱敏」。**建议重新生成一次环境 API Key**。

## 十、每日一问

> **你是怎么排除掉其他原因、锁定真正原因的？**

我没有靠「读代码猜」，而是靠**一条一条地把可能的链路掐掉**：

1. **先看数据，不看代码**。点完按钮后读页面自己的状态钩子 `window.__KQ_EVIDENCE()` —— `lastMissing` 里两个响应的完整体都在（PATCH 404 + DELETE 404）。这一步直接排掉了「网络不通 / 跨域拦住 / 接口坏了」这三大类猜测：**请求链路是通的**。
2. **再看异常的类型和位置**，而不是内容。打开调试器的 `setPauseOnExceptions('all')`，逼浏览器在异常发生的那一刻停下来 —— 拿到的是 `ReferenceError`，不是 `TypeError`、不是网络错。`ReferenceError` 只意味着一件事：**某个标识符在当前作用域里不存在**。这排掉了「函数内部逻辑写错」的可能。
3. **最后看行号**。异常抛在 `checkup.html:713:55`，正好是第二个 `.then` 回调里用到 `r1` 的那一行；回头比对第一个 `.then`，`r1` 恰恰只是它的形参。**一个变量只在 A 回调里声明、却在 B 回调里使用** —— 结论就唯一了。
4. **补一刀**：`.catch(function () {})` 解释了「为什么这个 Bug 能潜伏一整天」——它不是没有异常，是**异常被人为地藏了起来**。

用一句话概括方法：**先证明「不是别的地方」，剩下的那个就是原因**。而要做到这一点，前提是每一步都留下能被检查的痕迹（状态钩子、请求日志、异常断点），而不是只在脑子里推。
