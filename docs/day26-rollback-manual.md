# 回滚手册 · knowledge-quest

> 项目：knowledge-quest ｜ 定稿：2026-10-11（Day 26）｜ 配套：发布清单 `docs/day26-release-checklist.md`
>
> **核心前提**：本项目的静态托管用 `tcb hosting deploy` 上传，CLI 帮助原文写着
> **"file upload only, no version management"** —— 也就是说**平台侧没有版本层**。
> 因此"回退能力"完全建立在 **git 历史**上：能回退，是因为 git 里存着每一版的前端产物。
> **没有 git tag 和完整历史，就没有回滚。**（这也是"备份是资产，不是念头"的意思。）

---

## 一、回滚的边界（先想明白再动手）

| 回滚能解决 | 回滚不能解决 |
|---|---|
| **代码问题**：退回上一版部署，页面/接口恢复 | **数据问题**：被误删/写坏的数据，回滚代码不会把它们变回来 |
| 新版本引入的报错、白屏、功能不可用 | 平台侧配置变更（路由、额度耗尽、域名问题） |

**结论：回滚是止血，不是治病。** 它是用"丢掉新版本的全部改动"换取"立刻恢复可用"。
所以触发回滚的门槛要清楚（见第二节），别把样式错别字也当回事。

---

## 二、触发条件：什么情况必须回滚（Day 26 余力加练）

| 情况 | 回滚？ | 为什么 | 首选动作 |
|---|---|---|---|
| 首页白屏 / 打不开 / 一直加载不出来 | ✅ **立即** | 用户完全用不了，等于服务挂了 | 静态托管回退（第三层 ①） |
| 核心流程报错：翻面、闯关、增/改/删任一不可用 | ✅ **立即** | 主功能不可用 | 静态托管回退 |
| 大面积 5xx（健康接口或列表接口持续失败） | ✅ **立即** | 后端不可用 | 先查云函数；确认是新版引起 → 云函数回退（第三层 ②） |
| 数据被写坏 / 被误删 / 表被改坏 | ⚠️ **回滚救不了** | 回滚只换代码，不还数据 | 用发布前备份**重新导入**（第三层 ③） |
| 密钥/凭据被提交进仓库 | ✅ **立即** | 安全红线，等待就是扩大暴露面 | 先轮换密钥，再回退到不含泄露的版本 |
| 只是样式错位、文案错别字 | ❌ 不回滚 | 不影响使用，回滚的代价（丢改动）更大 | 记 issue，下个版本顺手修 |
| 单个边缘用例出错（如超长输入提示不友好） | ❌ 不回滚 | 影响面小 | 记 issue |
| 「感觉不对 / 好像变慢了」 | ❌ 不回滚 | 没有可复核的证据 | 先取证（跑 `verify-project` + 看响应时间）再判断 |

**一条硬规矩**：**决定回滚前先取证**。至少拿到一条可复核的证据（错误码、白屏截图、接口返回），
否则容易在"其实只是自己浏览器缓存"上白折腾一轮（CDN 缓存几分钟是常态）。

## 三、分三层操作

### ① 代码回退：静态托管退回上一版 —— ✅ Day 26 已实操演练

> ⚠️ 平台没有版本层，所以"退回上一版"= **把上一版的构建产物重新上传**。
> 耗时实测与逐步记录见 `docs/day26-drill-log.md`。

```bash
# 0) 先确定要退回哪一版（tag 列表 / 最近提交）
git tag -l --sort=-creatordate | head
git log --oneline -10

# 1) 用 git worktree 把目标版本**签出成一个独立目录**（不动工作区、不动暂存区）
WT="D:/knowledge-quest/.rollback-wt"
git worktree remove --force "$WT" 2>/dev/null || true
git worktree add --detach "$WT" <目标commit>

# 2) 在那一版里跑**同一个部署脚本**（它自带白名单 + 站上残留清理）
cd "$WT" && bash cloudbase/deploy.sh <envId>
# 看第 5 步「部署生效自证」：health / 新版行为 / 前端生效 / 站点白名单 四项都要 OK

# 3) 验证"线上确实变了"
curl -s <SITE>/js/config.js | grep BUILD        # 应显示目标版本的 BUILD

# 4) 演练/事故结束后恢复最新版
cd - && git worktree remove --force "$WT"
bash cloudbase/deploy.sh <envId>                # 从工作区重新上传（= 最新版）
```

> ⚠️⚠️ **2026-10-11（Day 27）修正 —— 这条曾经害我们泄露了整个项目**：
> 旧写法是 `git archive <commit> | tar -x -C "$ROLLBACK_TMP"` 然后
> `hosting deploy "$ROLLBACK_TMP" /`。问题在于 `git archive` 导出的是**整个仓库根**
> （含 AGENTS.md / PRD.md / TECH_DESIGN.md / api-contract.md / `cloudbase/` 全部源码 /
> `db/schema.sql` / `docs/` 75 个文件），而 `hosting deploy` 传到 `/` 是**只覆盖不删除**的 ——
> 于是 122 个文件、27.7 MB 全落在公网站点根目录上，**任何人打开网址就能下载源码和设计文档**
> （实测 `curl .../cloudbase/deploy.sh` 返回 200 并输出脚本正文）。
>
> **新写法的两个关键点**：
> 1. **用 worktree 而不是 archive** —— 拿到的是一个正常的项目目录，于是可以走 `deploy.sh`，
>    而 `deploy.sh` 的构建是**白名单**的（`index.html` + `css/ js/ data/` + `tools/*.html`），
>    整仓里那些东西根本没机会被上传。
> 2. **`hosting deploy` 不删除** —— 所以"传错一次就永久留在公网"。因此 `deploy.sh` 现在
>    每次部署前会**清掉站上不属于站点的残留**（docs/ cloudbase/ db/ backups/ 根目录文档 / `tools/*.sh`），
>    并在第 5 步 ④ 用白名单做**行为自证**：站上出现白名单之外的文件 = 部署判定为失败。
>
> **教训**：回退脚本和发布脚本必须走**同一条构建路径**。两套路径 = 两套白名单 = 早晚有一边漏内容。

> ⚠️ 临时目录要放在仓库内但被忽略（本项目用 `.rollback-wt/`，已加进 `.gitignore`）——
> Windows 版 CLI 读不了 Git Bash 的 `/tmp`。

**回退的生效判据（本项目专用）**：线上 `js/config.js` 里的 **`BUILD` 标记**。
它是 Day 20 特意加在页脚上的"我到底跑哪一版"的自证标记 —— 回退成功 = 这个值变回旧版。

### ② 云函数回退：重新部署上一版代码 —— 📋 手册内容，不实操

> **为什么今天不实操**：今日任务清单明确把"云函数回退实操"列入「今日不做」；
> 且云函数今天没有代码变更（v1.0 的后端 = Day 24 那一版），回退它没有真实触发场景。
> 为了不制造无意义的生产变更，这条只写步骤、留给真出事时用。

```bash
# 1) 把后端目录切到目标版本（脚本部署的是**工作区内容**，所以必须先切工作区）
git checkout <目标commit> -- cloudbase/functions/

# 2) 重发云函数（Day 24 起脚本会自动自证是否真生效）
FORCE_FN=1 bash cloudbase/deploy.sh <envId>

# 3) 验证（同样不看时间戳，看"只在新版才成立的行为"）
curl -s <API>/cards/99999999999999999999      # 期望 500 + INTERNAL_ERROR + traceId
```

### ③ 数据恢复：只能用发布前导出的备份重新导入 —— 📋 手册内容，不实操

> **为什么今天不实操**：数据恢复会**真的写库**（甚至要先清空再回灌），在没有真实数据事故时
> 执行它本身就是一次生产风险；且今日任务把"数据恢复实操"列为「今日不做」。
> 只写步骤 + 强调"发布含表结构变更前必须先导出"。

```bash
# 前情：发布前已导出（Day 26 实做）
#   backups/cards_20261011.json        （26 行 / 9 字段）
#   backups/quiz_records_20261011.json （6 行 / 6 字段）
# 重新导出当前状态（回灌前先留一份"坏数据"证据）：
bash tools/backup-data.sh backups_broken

# 恢复做法（把备份里的行按 id 回灌）：
#   1) 若表被清空/损坏 → 先按 db/schema.sql 重建表结构
#   2) 用备份 JSON 生成 INSERT 语句，**显式带上 id**（id 是 serial，不显式指定会错位）
#   3) 回灌后把序列拨正：
#        SELECT setval(pg_get_serial_sequence('cards','id'), (SELECT MAX(id) FROM cards));
#   4) 核对行数：SELECT count(*) FROM cards;  应 == 备份里的 row_count
```

⚠️ **两条铁律**：
1. **发布内容包含表结构变更时，必须先导出数据再发布**（结构一变，旧备份可能对不上新表）。
2. 回灌要**显式带 id**，并在最后 `setval` 拨正序列 —— 否则新插入的行会撞主键（见 `db/seed.sql` 的写法）。

## 四、回滚后的验证方法

回滚做完不等于好了，必须逐项验：

| # | 验证项 | 命令 / 动作 | 期望 |
|---|---|---|---|
| 1 | 线上版本已变 | `curl -s <SITE>/js/config.js \| grep BUILD` | 等于目标版本的 BUILD |
| 2 | 页面可用 | 浏览器打开 `<SITE>/` | 正常渲染，无白屏 |
| 3 | 核心流程可用 | 翻面 → 闯关 → 添加卡片 → 刷新仍在 → 删除 | 全通 |
| 4 | 后端一致 | `bash tools/verify-project.sh` | 除 A6（BUILD 日期可能落后于最新提交）外应全 PASS |
| 5 | 数据未受损 | `SELECT count(*) FROM cards` / `quiz_records` | 与备份 `row_count` 一致 |

> ⚠️ 第 4 项有个已知例外：回退到旧版后，`A6` 可能报 FAIL（旧 BUILD 的日期早于前端最后提交日）。
> **这是预期的**——回滚状态下本来就不是"最新版"。此时以第 1/2/3 项的**行为验证**为准，
> 并在事后把 A6 的例外写进当日记录，而不是为了让检查变绿去改 BUILD。
