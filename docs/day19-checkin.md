## 一、今天做了什么

不写新功能，只做一次重构：把散在接口里的数据库代码拆成独立的**数据访问层**。

**拆之前**（Day 18 结束时的样子）：

| 文件 | 行数 | 里面装着什么 |
|---|---|---|
| `index.js` | 348 | 路由 + 响应形状 + CORS + 日志 **+ 两个表的查询条件拼装 + 全部校验规则** |
| `db.js` | 209 | 两张表的读与写 **+ HTTP 请求细节（域名/鉴权头/超时）** |

一个文件管好几件事，加一个接口就要再抄一遍查询；改表字段要改 N 处，漏一处就静默出错。

**拆之后**（4 层 8 个文件）：

```
cloudbase/functions/api/
├── index.js                    176 行  【入口层】路由 / 状态码 / 响应形状 / CORS / 日志
├── services/                           【业务层】规则
│   ├── validate.js              74 行   必填 / 长度 / 范围（中文报错）
│   ├── cardsService.js          86 行   卡片规则 + 防重复
│   └── quizRecordsService.js    93 行   战绩规则 + 防重复
├── repositories/                       【数据访问层】数据
│   ├── cardsRepository.js       73 行   cards 表：查 / 取 / 写 / 防重复查询
│   └── quizRecordsRepository.js 66 行   quiz_records 表：查 / 写 / 防重复查询
└── lib/gateway.js              105 行  【传输层】唯一发 HTTP 的地方
```

入口层从 **348 行瘦到 176 行**（-49%），`db.js` 按表拆成两个 repository，HTTP 细节下沉到传输层。

## 二、分层后的文件清单与职责

| 层 | 文件 | 放什么 | 不放什么 |
|---|---|---|---|
| 入口层 | `index.js` | 路由分发、path 归一化、状态码、`{ok,data,error}` 形状、CORS 白名单、服务端日志 | 任何字段规则、任何数据读写 |
| 业务层 | `services/` | 必填与长度、分数≤题数、日期格式、防重复怎么判、查不到算不算错 | HTTP 细节、查询语句 |
| 数据访问层 | `repositories/` | 查哪张表、什么条件、排序、写入并拿回新行（**一张表一个文件**） | 输入校验、状态码 |
| 传输层 | `lib/gateway.js` | 域名、鉴权头、超时、序列化、把非 2xx 转成异常 | 查哪张表、业务判断 |

## 四、自检 4 条（对应教材「今天怎么检测」）

### 1. 分层到位检测 —— 关键词搜索

教材原话是「在接口文件里搜 select、insert、update 等 SQL 关键字，再在 repository 文件里搜同样的关键字」。

**先说一个必须讲清的事实**：本项目走的是云数据库的 **HTTP 通道（PostgREST）**，代码里从来就没有 SQL 字符串——所以按教材原样搜 `select … from` / `insert into` / `update … set` / `delete from`，**接口层和数据访问层都是 0 命中**，这个检测在我们的项目上验不出东西。

**换成贴合本项目的「数据访问特征」来搜**（表名、查询参数、写库姿势），差别立刻出来了：

| 层 | 文件 | 命中 |
|---|---|---|
| 接口层 | `index.js` | **0** |
| 业务层 | `services/validate.js`、`cardsService.js`、`quizRecordsService.js` | **0** × 3 |
| 传输层 | `lib/gateway.js` | 3 |
| 数据访问层 | `repositories/cardsRepository.js` | 10 |
| 数据访问层 | `repositories/quizRecordsRepository.js` | 6 |

→ **接口层 0 命中、数据访问层全部命中 = 分层到位。** 截图 `kq_day19_search_1_interface.png`（第 1 张）与 `kq_day19_search_2_repository.png`（第 2 张）。

### 4. 结构可讲检测 —— 合上文档自己回答

教材问三句，我的答案：

- **入口层放什么？** 只放「HTTP 这件事」：路径匹配、状态码、响应包成 `{ok,data,error}`、跨域白名单、写一行日志。它认识 URL，不认识表。
- **数据访问层放什么？** 只放「这张表怎么读写」：查哪些字段、按什么条件、排什么序、写完怎么把新行拿回来。一张表一个文件，改字段只改这一处。
- **为什么接口里不许写查询？** 因为接口会越加越多，表就那么几张。查询写在接口里＝同一个表的读法被抄 N 份，改字段要改 N 处，漏一处就静默出错；收进 repository 后改一次全都跟着变，而且谁也没法绕过它偷偷查库。

## 七、今天最值得记的一件事：**检测方法要跟着项目形态走**

教材给的检测是「搜 SQL 关键字」——那是针对「SQL 直接写在代码里」的项目。我们这个项目走的是托管数据库的 HTTP 通道（PostgREST），**代码里根本没有 SQL 字符串**，所以照搬教材去搜，两边都是 0 命中：看起来「完美通过」，实际上什么都没验出来。

**关键在于把「检测目标」翻译成这个项目的形态**：既然数据访问表现为「表名 + 查询参数 + 写库偏好（Prefer）」，那就搜这些。换成这套关键字后，接口层 0 命中、数据访问层 19 处命中，分层是否到位立刻有了区分度。

这件事的普适版本是：**验收标准不能照抄，要翻译。**照抄的结果是走过场，翻译过才有证据力。

### 数据「不会去」的地方（反向声明）

- 表名与查询参数**不会**出现在入口层与业务层：对数据访问特征命中数为 0
- 校验逻辑**不会**出现在数据访问层：repository 不做任何输入判断，接到什么查什么
- 校验失败的请求**不会**到数据库：三条规则在调用 repository **之前**判定完毕，一次网络请求都不发
- HTTP 状态码**不会**出现在业务层以下：repository 一律抛异常，由入口层统一兜底成 500
- 用户输入**不会**拼进查询语句：条件是 URL 参数 / JSON 请求体，由服务端解析绑定

### 顺带记一件非技术的事

重构过程中出现过一次意外：`cloudbase/` 目录整个从工作区消失了（git 记录 7 个文件被删，其中只有 `db.js` 是我主动删的）。因为**改动还没提交、新文件还没进 git**，我用 `git checkout -- cloudbase/` 先把已追踪的 7 个文件从 HEAD 恢复，再把新写的 6 个文件重写了一遍，并立刻 `git add` 纳入索引——之后每次改完都先 add 再继续，避免同样的事再来一次。教训：**重命名/删除文件的操作，做完立刻验证目录还在。**

## 八、每日一问：

> **拆完之后，「查数据库」这段代码从哪移到了哪？**

以前它散在两个文件里：`index.js` 里拼查询条件、决定查哪张表，`db.js` 里发请求、解析返回，两张表还混在同一个文件中。

接口层只剩一行 `cardsService.list(event)`，它连表名都看不见。

怎么验证？在入口层和业务层搜数据访问特征，命中 **0**；在数据访问层搜，命中 **19** 处。
