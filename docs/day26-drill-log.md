## 四、演练中遇到的真实问题（这一节比"顺利跑完"更有价值）

**现象**：第 4 步恢复 v1.0 时，`deploy.sh` 返回码 `1`，线上仍是旧版。日志只有一行关键提示：

```
== 3/5 上传前端静态文件 ==
[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":61,"threshold":50,"targets":["/d/knowledge-quest/.cloudbase-dist"]}
         → 部署返回码 1
```

**根因**：`deploy.sh` 第 3 步的 `rm -rf "$DIST"`（清空构建目录）**被环境的批量删除保护拦下**——
因为我在之前几天的操作里往 `.cloudbase-dist/` 里堆了日志和临时导出，文件数达到 61 > 阈值 50。
`set -euo pipefail` 让脚本**当场退出**，于是前端根本没上传。

**处置**：把非构建产物（日志等）移出该目录 → 目录内文件数回落到 17 → 重跑 `deploy.sh` → 成功。

**这次失败反而验证了两件事**：

1. **`deploy.sh` 是"诚实的"**：它失败了就返回 1，**没有假装成功**。
   这正是 Day 24 修掉"容忍失败"之后的预期行为——老版本会打印警告然后以 0 退出，那才危险。
2. **"演练"的价值就在这**：如果只在纸面上写"重跑 deploy.sh 即可恢复"，
   真出事时遇到 `SAFE_DELETE_BULK_CONFIRM_REQUIRED` 会一头雾水。**这正是教材说的"没演练过的回滚等于没有回滚"。**

**顺手改进（当日第一次提交）**：给 `deploy.sh` 的这一步加了显式失败检查 + 人话提示，
以后看到这个错误能直接知道"卡在第 3 步、是清理被拦、把杂物移出去"：

```bash
if ! rm -rf "$DIST"; then
  echo "❌ 清理构建目录失败：$DIST" >&2
  echo "   常见原因：目录内文件过多，被环境的批量删除保护拦下（[safe-delete] 提示）。" >&2
  echo "   处置：把非构建产物（日志、临时导出）移出该目录后重跑。" >&2
  exit 1
fi
```

### 4.1 补记：同一天第二次撞上同一个坑 —— 于是把"消除触发条件"做成了根治

**为什么会有第二次**：回退演练需要**再补三张截图**（v1.0 线上 / 回退后 / 恢复后），
于是把整条演练重跑了一遍。重跑时 `.cloudbase-dist/` 又因为累积变动重新超过阈值，
`deploy.sh` **再次返回 1、前端再次没上传**。更糟的是脚本里那句日志骗了人：

```bash
bash cloudbase/deploy.sh "$ENV" >> "$LOG" 2>&1
say "[$(ts)] deploy.sh 返回码 $?"      # ❌ 假数据：$(ts) 先执行，$? 读到的是 ts 的返回码（恒为 0）
```

结果日志上写着「返回码 0」，线上其实还是旧版 —— **这正是 Day 24 总结的"会撒谎的脚本"，
只不过这次撒谎的是我自己的演练脚本**。所以：

| # | 改动 | 文件 | 性质 |
|---|---|---|---|
| ① | 构建改为 **staging + `mv`**：先构建到 `.cloudbase-dist.stage`（二十来个文件），再把旧构建目录 `mv` 进 `.cloudbase-trash/`（**mv 不是删除，不触发批量删除保护**），最后 staging 改名成正式目录 | `cloudbase/deploy.sh` 第 3 步 | **根治**：不再依赖"先删干净再重建"这条必然踩坑的路 |
| ② | 新增第 5 步 ③ **前端生效自证**：托管域名上 `js/config.js` 的 `BUILD` 必须与本地一致（带 `Cache-Control: no-cache` + 3 次重试，防 CDN） | `cloudbase/deploy.sh` 第 5 步 | **根治**：前端没上传成功从此**不可能**被漏掉（Day 26 之前它一直是隐形的） |
| ③ | 修正假返回码：先把 `$?` 存进变量再打印；恢复失败就**不出第三张图** | `kq26_shots.sh` | 修掉"会撒谎的演练脚本" |
| ④ | 新增临时目录清理入口；`.gitignore` 补 `.cloudbase-dist.stage/`、`.cloudbase-trash/` | `tools/clean-trash.sh`、`.gitignore` | 收拾根治方案的副作用 |

**修完实跑验证（2026-10-11 12:2x）**：`deploy.sh` → `EXIT=0`，第 5 步自证三行全 OK：

```
  [health]     OK   后端活着
  [新版行为]   OK   5xx 走统一出口（INTERNAL_ERROR + traceId）→ 线上代码确实是新版
  [前端生效]   OK   托管域名上的 BUILD = 本地（v1.0-2026-10-11）→ 前端确实换成这一版了
```

**这一节是本次演练最大的收获**：如果只写一句"重跑 `deploy.sh` 即可恢复"，真出事时
既会遇到 `SAFE_DELETE_BULK_CONFIRM_REQUIRED` 一头雾水，又会被假返回码骗过去。
**"没演练过的回滚等于没有回滚"——第一次撞上叫运气，第二次撞上才叫修复。**

### 4.2 补图轮（第二轮）又抓出两个坑

第二次跑是**为了补齐三张截图**，结果又暴露两件事——都不是"部署/回滚"本身的问题，
但每一个都会让人**误判线上状态**：

**坑 A：CloudBase 默认测试域名的「页面访问提示」护栏页**

新建的浏览器 profile 首次访问 `*.tcloudbaseapp.com` 时，腾讯云会先塞一页
「页面访问提示 / 我是开发者，如何去掉当前页面? / **[确定访问]**」。
这一页是**平台塞在页面里的**，`KQ_CONFIG` 根本不存在 → 脚本读到 `BUILD=null`、
PrintWindow 抓到的是一张 **144 KB 的"风险提醒"图**（内容区是护栏页，不是我们的应用）。
之前几轮没撞上，只是因为那个 profile 里已经有"已确认访问"的记忆。

对策：读取脚本在轮询时**自动点掉护栏按钮**（`确定访问/继续访问/确认访问/我知道了`），
再继续等待 `BUILD` 出现。实测输出 `GUARD=clicked:确定访问` → 随后 `BUILD=v1.0-2026-10-11`。
另外 `kq26_shot.py` 加了**字节数自检**（< 300 KB 就判定"疑似空白图"并告警），
这次的 144 KB 假图就是被它拦下来的 —— **截图工具也得有判据，不然空白图会当成证据交上去**。

**坑 B：同一套命令，上传耗时差了 7 倍**

| 轮次 | `hosting deploy`（回退上传 123 个文件）耗时 |
|---|---|
| 第一轮（计时用） | **13 秒** |
| 第二轮（补图用） | **98 秒** |

同一台机器、同一批文件、同一条命令。结论：**回滚耗时有很大方差，不能拿一次的数字当预算**。
所以手册里不该写"回滚约 1 分钟"，应该写"**实测 13 秒 ~ 98 秒，取决于网络**"——
真正稳定的是**流程本身**：导出 → 上传 → 用 `BUILD` 标记判生效。

上面第一轮的 51 秒是"执行脚本时顺带记的"，容易被人质疑"是不是随手写的"。

| 2 | 第三节 ① 第 2 步 | 补预期耗时与提示：**"上传 13~98 秒，没有进度条属正常；等它打印『部署生效自证：全部通过』再往下"** |
| 3 | 第三节 ① 第 3 步 | 补**成功长什么样**：**"输出的 `BUILD` 变成 `d25-2026-10-11` 即为退回成功；确认后立刻执行第 4 步，别停"** |

## 八、结论

**回滚演练花了多久？**

答两个数字，因为这是**两个不同的问题**：

| 问的是 | 答案 |
|---|---|
| 机器跑完这套流程要多久 | **51 秒**（导出 22 s ＋ 上传 13 s ＋ 验证 14 s）；复测轮 112 秒。整场约 3 分钟 |
| **由真人照手册操作要多久** | 回退阶段 **76 秒**、**整场 11 分 41 秒**（10-12 本人亲手操作）。其中机器执行只有 2 分 24 秒，**其余 9 分 17 秒是人在读和判断** |

**真出事敢不敢用这套流程？**
**敢，但有三个前提**，缺一个就会手忙脚乱：

1. **git 里有完整历史和 tag** —— 因为平台**没有版本层**（`hosting deploy` 帮助原文：*no version management*），
   回退能力完全建立在 git 上。没有 tag 和完整历史，这个速度不存在。
2. **知道用 `BUILD` 标记判断"现在是哪一版"** —— 而不是猜、不是看时间戳。
3. **接受"回滚只治代码"** —— 数据出问题必须靠发布前导出的备份（`backups/*.json`）重新导入，
   这条**今天没实操**（今日不做），所以真出事时它是全套流程里**唯一没被验证过的一环**——
   这是已知的薄弱点，已登记在案（Day 27 会做资源检查与备份演练）。
