## 二、接线后的文件与职责

### 接口地址收敛到一处（这是今天结构上最重要的一件事）

```
js/config.js          ← 全站唯一的接口地址定义点（KQ_CONFIG）
   ├── js/main.js       首页：只读 KQ_CONFIG.API_BASE，不再自己拼地址
   ├── js/quiz.js       闯关：同上
   ├── js/gallery.js    展览：同上
   └── tools/checkup.html  检查台：同上
```

**为什么前端不叫"环境变量"**：纯静态页面在构建时没有注入环节、运行时也没有 `process.env`。
对静态站来说，**一个 JS 常量文件就是它的 `.env`**。所以 `js/config.js` 里还顺手放了两个防呆自检——
地址为空、或末尾多写一个 `/`（会拼出 `//cards`）都会立刻抛错，而不是等 fetch 报一句看不懂的话。

`js/config.js` 另外带一个 **`BUILD` 标记**（当前 `d20-2026-10-06`），页脚会把它打出来。
这东西的作用很实在：以后"改了没生效"这种假故障，看一眼页脚就知道线上跑的是哪一版。

## 七、今天最值得记的一件事：**跨域那一下，我是怎么认出问题出在哪的**

### 7.1 先认"长什么样"

跨域失败的症状是固定的三件套：**页面能打开 + 数据是空的 + F12 控制台有红色报错，关键词 `Access-Control-Allow-Origin`**。
记住这三条的意义在于：**它和"接口挂了"（500/timeout）和"路径写错"（404）表现完全不同**，
只要看到"页面开着但数据空"，第一反应就该是查响应头，而不是去改代码。

### 7.2 本项目的跨域是怎么配的（和教材例子不一样，得说清楚）

教材的案例是去 **CloudBase 控制台 → 云函数 → HTTP 访问服务 → 跨域配置** 填域名。
本项目走的是**另一种同样正规的做法：跨域在云函数里做白名单回显**——请求带 `Origin`，
函数判断它在不在白名单里，在就回显这个 `Origin`，不在就不回这个头。

**为什么不用控制台那一处**：Day 17 记录过，当前是体验版环境，控制台的安全域名配置有门槛；
而"函数侧回显"的好处是**白名单写在代码里、跟仓库一起版本化**，改了什么 `git diff` 看得见。

**为什么坚决不写 `*`**：`*` 等于对全世界任何网站开放接口。今天这个接口有写能力（POST），
用通配符等于把写能力交出去。所以白名单只放三个来源：GitHub Pages、CloudBase 静态托管、本机调试地址。

### 7.3 怎么"确认它是对的"——用响应头说话，不用肉眼

动手改前端之前，先把三种情况各发了一次请求：

| 请求 | 期望 | 实测 |
|---|---|---|
| `Origin: https://xingho-vibecoding.github.io`（白名单内） | 有 `Access-Control-Allow-Origin` 且等于自己 | ✅ 回显该 Origin |
| `Origin: https://zgr...-1500012353.tcloudbaseapp.com`（白名单内） | 同上 | ✅ 回显该 Origin |
| `Origin: https://evil.example.com`（白名单外） | **没有任何** `Access-Control-Allow-Origin` | ✅ 无该头（浏览器此时会拦掉响应） |
| `OPTIONS /api/cards`（预检，带 `Access-Control-Request-Method: POST`） | 200 + 允许的方法/头 | ✅ 通过 |

**这就是"认出问题出在哪"的方法**：不要等到页面报红才去猜，
先用 `curl -H "Origin: ..." -D -` 把响应头摊开看——**跨域问题是"响应头里少了一行"，不是"接口坏了"**。
一旦确认白名单里外行为不同，页面还连不上时，就能立刻把嫌疑排到别处（比如地址写错、缓存没刷新）。

## 八、每日一问

> **跨域那一下，你是怎么认出问题出在哪的？**

**答**：靠"症状 → 响应头 → 三方对照"这三步，而不是靠猜。

1. **先认症状**：跨域失败的样子很固定——页面能打开、数据是空的、F12 控制台红字里有 `Access-Control-Allow-Origin`。
   这个组合跟"接口 500"和"路径 404"完全不同，看到它就该往跨域想，而不是去翻业务代码。
2. **再摊开响应头**：用 `curl -H "Origin: <我的域名>" -D -` 直接看返回头里有没有 `Access-Control-Allow-Origin`、值是不是我自己。
   **跨域问题的本质是"响应头少了一行"**，所以要看头，不要看页面。
3. **然后做三方对照**：白名单内两个域名各发一次（应该有）、白名单外发一次（**必须没有**）。
   三次结果都对得上，才能说"跨域配置是对的"；如果白名单外也回了头，那说明白名单写成了 `*`，是更严重的问题。
4. **最后看预检**：带 `OPTIONS` 和 `Access-Control-Request-Method` 发一次，确认非简单请求（我们的 POST 带 JSON）能过。

补充一句更重要的：**今天我根本没遇到跨域报错**——不是运气好，是因为在动手前就用上面这套方法把链路验了一遍，
所以问题在"还没发生"的时候就被拦住了。**这就是"认出问题出在哪"的更高一层：在它出现之前先证明它不会出现。**
